# Repository search practices for coding agents

This note separates **source-backed observations** from **measured benchmark evidence** and **rstack synthesis**. Tool specifications describe what a search can return; they do not establish that a coding agent will choose the right query, inspect every relevant boundary, or recognize that an empty result is inconclusive. The recommendations below are therefore labeled **Rstack synthesis**. All sources were accessed **2026-08-25**.

## Source-backed observations

### Match the operation to the question

* **Filename/layout discovery.** Git describes a pathspec as a pattern that limits the paths considered by commands including `git ls-files` and `git grep`; a pathspec can constrain a directory prefix, use pathname globbing, anchor at repository root with `top`, or use literal matching. ([Git glossary — pathspec](https://git-scm.com/docs/gitglossary#Documentation/gitglossary.txt-pathspec)) `git ls-files` can list tracked files, untracked files, ignored files, modified files, and files in the index/working tree through distinct options, so “find the file” must state which of those populations is intended. ([git-ls-files](https://git-scm.com/docs/git-ls-files))

* **Literal and regular-expression search.** ripgrep searches files line by line and prints lines matching the supplied pattern; it supports literal patterns and regular expressions, with `-F` forcing literal interpretation. ([ripgrep Guide — Basics](https://github.com/BurntSushi/ripgrep/blob/master/GUIDE.md#basics)) This makes literal search appropriate for exact spellings, serialized keys, command flags, and error text, while regex is appropriate when spelling/format varies; neither operation establishes symbol identity or call-graph reachability. The final limitation follows from the documented line-by-line matching model. ([ripgrep Guide — Basics](https://github.com/BurntSushi/ripgrep/blob/master/GUIDE.md#basics))

* **Structural search.** ast-grep parses a pattern as code and matches it against AST nodes; its pattern can match nested expressions and is independent of whitespace/newline layout. ([ast-grep Pattern Syntax — Pattern Matching](https://ast-grep.github.io/guide/pattern-syntax.html#pattern-matching); [ast-grep Quick Start — Pattern](https://ast-grep.github.io/guide/quick-start.html#pattern)) A single `$META` matches one AST node, `$$$` matches zero or more nodes, and repeated metavariable names require the same AST content; these are structural constraints rather than textual wildcards. ([ast-grep Pattern Syntax — Meta Variable](https://ast-grep.github.io/guide/pattern-syntax.html#meta-variable); [Multi Meta Variable](https://ast-grep.github.io/guide/pattern-syntax.html#multi-meta-variable); [Meta Variable Capturing](https://ast-grep.github.io/guide/pattern-syntax.html#meta-variable-capturing)) The pattern must be valid code for the selected tree-sitter parser, and ast-grep documents language inference from file extensions or explicit `--lang`; malformed or wrongly contextualized patterns therefore need a parse/context diagnosis rather than being treated as proof of absence. ([ast-grep Pattern Syntax — Pattern Matching](https://ast-grep.github.io/guide/pattern-syntax.html#pattern-matching); [ast-grep Quick Start — Pattern](https://ast-grep.github.io/guide/quick-start.html#pattern))

* **Semantic symbol navigation.** LSP defines separate requests for go-to-definition, references, implementations, and workspace symbols, and describes each as a language-server feature rather than a textual search. ([LSP 3.17 specification — `textDocument/definition`](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/#textDocument_definition); [`textDocument/references`](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/#textDocument_references); [`textDocument/implementation`](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/#textDocument_implementation); [`workspace/symbol`](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/#workspace_symbol)) LSP clients and servers exchange capabilities during initialization, and the specification explicitly notes that a server may support one feature but not another, including `workspace/symbol`. ([LSP 3.17 specification — Capabilities](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/#capabilities)) A missing definition/reference/implementation result is therefore evidence about that server/index/configuration at that moment, not a universal proof that no such code exists.

* **Use more than one operation when the question changes.** Definition answers “where is this symbol defined”; references answer “where does the server resolve uses”; implementations answer a related polymorphic-navigation question; workspace symbols search server-provided symbol information. ([LSP 3.17 specification — definition](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/#textDocument_definition); [references](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/#textDocument_references); [implementation](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/#textDocument_implementation); [workspace symbols](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/#workspace_symbol)) A behavior question still needs textual/structural searches for configuration, strings, generated inputs, tests, and runtime wiring because LSP navigation is scoped to what the language server models and exposes. This last sentence is **Rstack synthesis** based on the protocol’s feature/capability boundary and the textual/AST models documented by ripgrep and ast-grep. ([LSP Capabilities](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/#capabilities); [ripgrep Basics](https://github.com/BurntSushi/ripgrep/blob/master/GUIDE.md#basics); [ast-grep Pattern Matching](https://ast-grep.github.io/guide/pattern-syntax.html#pattern-matching))

### Narrowing, widening, and ignore behavior

* ripgrep recursively searches the current directory by default, but its documented default filtering excludes paths matched by `.gitignore`, `.ignore`, and `.rgignore`, hidden files/directories, binary files, and symlinks. ([ripgrep Guide — Automatic filtering](https://github.com/BurntSushi/ripgrep/blob/master/GUIDE.md#automatic-filtering)) `--no-ignore`, `--hidden`, `--text`, and `--follow` independently relax those filters; repeated `-u` progressively disables ignore, hidden, and binary filtering. ([ripgrep Guide — Automatic filtering](https://github.com/BurntSushi/ripgrep/blob/master/GUIDE.md#automatic-filtering)) A search result is therefore inseparable from its root, path globs, file-type filters, ignore mode, hidden/binary/symlink mode, and configuration.

* ripgrep’s manual globs are processed in order, and later globs override earlier ones; a non-blacklist glob causes every searched file to need a match, while a later blacklist can exclude it. ([ripgrep Guide — Manual filtering: globs](https://github.com/BurntSushi/ripgrep/blob/master/GUIDE.md#manual-filtering-globs)) File types are named collections of globs and can be included or excluded, with `--type-list` exposing the actual mapping. ([ripgrep Guide — Manual filtering: file types](https://github.com/BurntSushi/ripgrep/blob/master/GUIDE.md#manual-filtering-file-types)) Narrowing by a guessed extension or type can silently exclude extensionless scripts, generated files, templates, or unusual language files; the extensionless-file behavior is explicitly illustrated for the `sh` type. ([ripgrep Guide — The special `all` file type](https://github.com/BurntSushi/ripgrep/blob/master/GUIDE.md#the-special-all-file-type))

* ripgrep reads options from `RIPGREP_CONFIG_PATH` when that environment variable is set; the config is prepended to explicit arguments, so command-line options generally override it, and `--debug` reports the loaded config and arguments. ([ripgrep Guide — Configuration file](https://github.com/BurntSushi/ripgrep/blob/master/GUIDE.md#configuration-file)) The guide specifically recommends `--debug` when no files were searched because a home-level ignore rule may be responsible. ([ripgrep Guide — Basics](https://github.com/BurntSushi/ripgrep/blob/master/GUIDE.md#basics)) An empty result must therefore preserve and report effective configuration rather than collapsing “not matched” and “not searched.” (**Rstack synthesis**.)

* Git’s ignore rules are intentionally for untracked files; already tracked files are not affected. Git evaluates command-line patterns, nested `.gitignore` files, repository `info/exclude`, and `core.excludesFile` with documented precedence, and build-generated files are a stated reason projects commonly include `.gitignore` patterns. ([gitignore](https://git-scm.com/docs/gitignore#_description)) A negated pattern cannot re-include a file if a parent directory is excluded, because Git does not descend into excluded directories. ([gitignore — Pattern format](https://git-scm.com/docs/gitignore#_pattern_format)) Ignored output may be diagnostically important even though normal source search omits it.

* Git pathspec exclusions are applied after a path matches a non-exclude pathspec; with no non-exclude pathspec, exclusion applies as if no pathspec was supplied. ([Git glossary — exclude pathspec](https://git-scm.com/docs/gitglossary#Documentation/gitglossary.txt-exclude)) This gives a precise way to express “search this known subtree except generated/vendor output,” but it does not prove that a repository’s chosen `vendor`, `dist`, `build`, or generated directory is semantically irrelevant.

* **No universal vendor/generated/build rule.** The Git and ripgrep sources document mechanisms and repository/user policy files, not a universal policy that every `vendor/`, `generated/`, `dist/`, `target/`, or `build/` path should be skipped. The evidence supports treating those directories as an explicit scope decision, not as an unexamined default. (**Rstack synthesis; no authoritative source found supporting a universal skip rule.**)

### Exact symbols versus behavior and concepts

* The TypeScript module reference documents named exports/re-exports, namespace imports, CommonJS `require`/`module.exports`, type-only imports/exports that are elided from emitted JavaScript, and ambient modules that describe runtime-provided modules without a corresponding file. ([TypeScript Modules Reference — importing/exporting declarations](https://www.typescriptlang.org/docs/handbook/modules/reference.html#exporting-and-importing-typescript-specific-declarations); [type-only imports and exports](https://www.typescriptlang.org/docs/handbook/modules/reference.html#type-only-imports-and-exports); [ambient modules](https://www.typescriptlang.org/docs/handbook/modules/reference.html#ambient-modules)) Consequently, searching only for a declaration’s defining spelling can miss the public alias, re-export barrel, emitted/runtime form, or declaration-only path that callers use. This is **Rstack synthesis** from the documented language forms; it is not a claim that every language or agent exhibits the same miss.

* A literal/regex query is evidence of text; an AST query is evidence of parsed syntax; an LSP result is evidence of a server’s semantic index. Those evidence types have different blind spots by construction: textual search can find configuration and arbitrary strings but cannot resolve identity; AST matching can reject comments/strings and match syntax despite whitespace, but requires parseable code; LSP can resolve language-specific identity but only where the server supports and indexes the feature. ([ripgrep Basics](https://github.com/BurntSushi/ripgrep/blob/master/GUIDE.md#basics); [ast-grep Pattern Matching](https://ast-grep.github.io/guide/pattern-syntax.html#pattern-matching); [LSP Capabilities](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/#capabilities))

* **Rstack synthesis:** classify the query before choosing a tool: (1) path/layout, (2) exact token or serialized/config value, (3) spelling/format variants, (4) syntax shape, (5) resolved symbol/call/reference, or (6) user-visible behavior/concept. For (6), derive several observable terms and entry points, then combine text/AST/LSP searches and inspect tests/configuration/runtime boundaries; do not pretend that a single semantic query can answer a behavioral question. This decision rule is a synthesis of the distinct capabilities above, not a rule stated by any one source.

### Aliases, re-exports, reflection, generated code, config, tests, and runtime boundaries

* Re-export and alias forms are documented language behavior, not search-tool anomalies: TypeScript allows `export { f }`, namespace access, CommonJS `module.exports`, and ambient declarations for modules that exist at runtime without a local file. ([TypeScript Modules Reference](https://www.typescriptlang.org/docs/handbook/modules/reference.html)) **Rstack synthesis:** after finding a definition, inspect imports/exports and package entry points in both directions; search the exported/public name, local name, module path, and barrel/index files. If an LSP server is available, compare definition and references at both the local and public symbol positions. LSP capability limits mean this comparison is a confidence check, not a guarantee. ([LSP definition](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/#textDocument_definition); [LSP references](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/#textDocument_references); [LSP Capabilities](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/#capabilities))

* Reflection, string-based dispatch, dependency injection, generated source, templates, and external configuration do not have a single universal repository-search protocol. ripgrep can find their strings and files, ast-grep can find only parseable syntax, and LSP only reports what its language server models. ([ripgrep Basics](https://github.com/BurntSushi/ripgrep/blob/master/GUIDE.md#basics); [ast-grep Pattern Matching](https://ast-grep.github.io/guide/pattern-syntax.html#pattern-matching); [LSP Capabilities](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/#capabilities)) **Rstack synthesis:** when behavior crosses a runtime boundary, search the registration key/event/route/CLI/config name, the loader or dispatcher, the generated-input/template owner, and the tests or executable entry point—not only the implementation symbol. **No authoritative benchmark evidence was found that quantifies “agents commonly miss reflection” or any other specific boundary at repository scale; report this as a risk hypothesis, not a measured prevalence claim.**

* The IssueExec benchmark’s abstract reports that issue descriptions have an abstraction gap from implementation code, that existing tests covered 96.98% of ground-truth files in its 18-repository study, and that a two-hop issue→test→code path had stronger semantic connectivity than direct matching in 82.4% of cases. ([IssueExec](https://arxiv.org/abs/2607.17286)) Those are measured results for that benchmark and methodology, not a universal guarantee that tests exist, are current, or cover every runtime path. **Rstack synthesis:** for behavior questions, include test names, fixtures, snapshots, integration tests, and executable examples as search terms and evidence; treat missing tests as an uncertainty to report rather than proof that behavior is absent.

* Configuration is often a separate evidence population. ripgrep’s guide documents explicit glob/type filtering and an external configuration file that changes effective arguments. ([ripgrep Manual filtering: globs](https://github.com/BurntSushi/ripgrep/blob/master/GUIDE.md#manual-filtering-globs); [ripgrep Configuration file](https://github.com/BurntSushi/ripgrep/blob/master/GUIDE.md#configuration-file)) **Rstack synthesis:** search manifests, build files, CI/workflow files, environment/example files, deployment files, feature flags, and test configuration separately from source-code searches; record the active profile/target/environment when behavior may vary. Do not infer runtime configuration from a default file alone.

### Empty, incomplete, or conflicting results

* LSP’s specification says a response value of `null` indicates no result and does not tell the client to resend the request. ([LSP 3.17 specification — language-server results](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/#languageServerProtocol)) The same specification says capabilities are exchanged because not every language server supports every feature. ([LSP Capabilities](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/#capabilities)) **Rstack synthesis:** distinguish “unsupported,” “server returned no result,” “wrong document position,” “stale/incomplete index,” and “semantically absent”; fall back to textual/structural searches and state which checks were possible.

* ripgrep documents that no-file/no-match situations can be diagnosed with `--debug`, including identifying a loaded config, and that its automatic filtering may hide ignored, hidden, binary, or symlinked files. ([ripgrep Basics](https://github.com/BurntSushi/ripgrep/blob/master/GUIDE.md#basics); [Automatic filtering](https://github.com/BurntSushi/ripgrep/blob/master/GUIDE.md#automatic-filtering)) **Rstack synthesis:** an empty result should trigger one controlled widening step: verify root and query mode; inspect ignore/config diagnostics; include likely hidden/generated/vendor/config/test paths where relevant; vary exact term to aliases and behavior terms; then stop and report residual uncertainty rather than endlessly broadening.

* ast-grep requires a valid parser-compatible pattern and provides a playground to confirm how a pattern is parsed. ([ast-grep Pattern Syntax](https://ast-grep.github.io/guide/pattern-syntax.html#pattern-matching)) **Rstack synthesis:** an empty structural result should be classified as parse/grammar mismatch, scope/filter exclusion, or genuine no-match; test a smaller pattern and a known positive example before widening the repository.

### Benchmark evidence about agent/harness mistakes

* SWE-Explore isolates repository exploration from final patch success: an explorer must return a ranked list of relevant code regions under a fixed line budget. Its abstract reports 848 issues across 10 languages and 203 repositories, with line-level ground truth derived from successful repair trajectories; it finds file-level localization relatively strong while line-level coverage and efficient ranking remain differentiating weaknesses. ([SWE-Explore](https://arxiv.org/abs/2606.07297)) This directly supports guarding against “right file, wrong lines” and context-budget waste, but it does **not** prove a particular CLI, harness, or failure frequency in this repository.

* CORE-Bench defines repository retrieval as navigating a concrete repository state, locating relevant files/functions, gathering supporting context, and filtering in-repository distractors; its abstract reports more than 180,000 queries and 106,000 broader-context labels, with a sharp drop from traditional code search to requirement-driven repository retrieval. ([CORE-Bench](https://arxiv.org/abs/2606.11864)) This supports treating issue/concept search as a different task from docstring-to-function lookup, but its embedding experiments do not establish that a given coding agent made a specific mistake.

* The benchmark sources above provide evidence for localization difficulty, context efficiency, distractors, and issue-to-code abstraction gaps. They do not provide authoritative prevalence estimates for claims such as “agents always use grep,” “agents commonly ignore generated code,” “agents miss aliases,” or “agents stop after the first match.” **No authoritative primary evidence was found for those exact common-mistake claims; they should not be presented as measured facts.** The defensible design response is to make scope, query variants, search modes, and evidence explicit, and to measure the harness’s own outcomes later. (**Rstack synthesis**.)

## Rstack synthesis: proposed search protocol

1. **State the search question and evidence target.** Record whether the request asks for a path, exact spelling, syntax shape, resolved symbol, call/reference set, configuration owner, or behavior. Extract identifiers, aliases, data shapes, user-visible terms, likely entry points, and likely owners before invoking a search. This is a design recommendation derived from the distinct evidence models above, not a tool guarantee.
2. **Establish repository scope.** Record repository root, current revision/worktree, tracked versus untracked population, language/build targets, and whether generated/vendor/build output is in or out of scope. Use filename discovery/pathspecs to identify candidate areas before recursive content searches. ([git-ls-files](https://git-scm.com/docs/git-ls-files); [Git pathspec](https://git-scm.com/docs/gitglossary#Documentation/gitglossary.txt-pathspec))
3. **Start with the narrowest high-signal mechanism.** Use an exact symbol’s LSP references/definition/implementation when a working server and project context exist; use ast-grep for a known syntax shape; use literal/regex for text/config/behavior terms; use path discovery for layout. ([LSP navigation](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/); [ast-grep Pattern Syntax](https://ast-grep.github.io/guide/pattern-syntax.html); [ripgrep Basics](https://github.com/BurntSushi/ripgrep/blob/master/GUIDE.md#basics))
4. **Widen deliberately, not reflexively.** If results are empty or suspiciously narrow, first validate root, parser/language, LSP capability/index status, ignore/config settings, and file population. Then widen one dimension at a time: path scope, file types, ignore/hidden/generated/vendor inclusion, spelling variants, aliases/re-exports, behavior terms, tests/config, and runtime-boundary registration keys. Record each widening step and what it changed. ([ripgrep Automatic filtering](https://github.com/BurntSushi/ripgrep/blob/master/GUIDE.md#automatic-filtering); [ripgrep Configuration](https://github.com/BurntSushi/ripgrep/blob/master/GUIDE.md#configuration-file); [LSP Capabilities](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/#capabilities))
5. **Trace the evidence chain.** For a candidate implementation, inspect definition→references/callers, imports/exports, configuration and build ownership, tests/fixtures, generated-input owners, and entry/runtime wiring. Separate direct matches, semantically resolved results, and inferred links; cite file paths and line/range evidence in the final report. This is **Rstack synthesis** grounded in the separate textual, AST, LSP, module, configuration, and benchmark evidence above.
6. **Stop on explicit criteria.** Stop when the requested question has a corroborated evidence chain across the relevant boundary types, or when bounded widening yields no corroborating evidence and the remaining uncertainty is named. Stop/escalate on unsupported LSP features, unavailable parser/index, ignored or inaccessible populations, unresolved alias/reflection/generated/runtime ownership, contradictory results, or inability to establish the active configuration. Avoid a fixed “N searches” rule: the sources establish different failure modes, while the stopping threshold is a harness policy. (**Rstack synthesis**.)
7. **Report negative evidence precisely.** State the exact root, revision, command/tool mode, filters/ignore policy, query variants, paths searched, and whether the result was no-match, not-searched, unsupported, or unresolved. Include excluded populations and the next highest-value check when work must stop. A negative conclusion should be phrased as “not found under these scope and evidence conditions,” not “does not exist.” (**Rstack synthesis**.)

## Concrete task 9 design decisions and questions

1. **Decision:** make the skill’s first output a structured search contract: question type, identifiers/behavior terms, repository root/revision, intended file population, and likely language/build context. **Question:** which fields are mandatory before a search can run, and which may be inferred then explicitly reported?
2. **Decision:** use a tool hierarchy keyed to evidence type—pathspec/`git ls-files` for layout, LSP for resolved symbol navigation when capability/index checks pass, ast-grep for parseable syntax, and ripgrep for literals/regex/config/behavior terms. **Question:** which LSP clients/languages are actually available in the harness, and what is the fallback contract when capability or index checks fail?
3. **Decision:** treat ignore rules, hidden files, symlinks, binary files, generated output, vendor trees, and build output as named scope decisions rather than silently excluded or silently included. **Question:** which repository-local policies should override the default, and what bounded widening is allowed for each population?
4. **Decision:** require at least one controlled widening pass for empty/suspicious results and classify the result as no-match, not-searched, unsupported, parse-mismatch, or unresolved. **Question:** what observable threshold makes a result “suspiciously narrow,” and who/what authorizes further widening?
5. **Decision:** for behavior questions, require a chain that includes implementation plus relevant callers/registration, configuration/build ownership, tests/fixtures, and runtime/generated boundaries where applicable. **Question:** which boundary types are required for each task class, and what counts as sufficient corroboration?
6. **Decision:** report evidence with exact paths/ranges, search modes/filters, excluded populations, query variants, and unresolved uncertainty; never report a bare “not found.” **Question:** should the report be machine-readable, human-readable, or both, and which fields downstream `docs-sync`/OKF work consumes?
7. **Decision:** do not encode unmeasured folklore as a rule. Benchmark search quality later using line-level coverage, ranking/context efficiency, distractor handling, and issue-to-code/test localization metrics suggested by SWE-Explore, CORE-Bench, and IssueExec. ([SWE-Explore](https://arxiv.org/abs/2606.07297); [CORE-Bench](https://arxiv.org/abs/2606.11864); [IssueExec](https://arxiv.org/abs/2607.17286)) **Question:** what repository-local acceptance scenarios will measure missed aliases, ignored/generated paths, empty-result recovery, and runtime-boundary tracing without claiming universal agent behavior?
